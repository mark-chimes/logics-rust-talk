\begin{block}{Lambda representation}
\[\texttt{inc} \equiv \lambda x.\ x + 1\]
\end{block} 
maps natural numbers to natural numbers
\begin{block}{}
\[
\texttt{inc} : 
\mathsf{int}\{v: 0 \leq v\} \rightarrow \mathsf{int}\{v : 0 \leq v\}
\]
\end{block}
\end{frame}

\begin{frame}{Typing Judgements} 
First, we would need a rule about the type of our function. 

We can assume we have a \emph{typing context} $\Gamma$. This contains 
variable bindings like $x : int$. 

A judgement like 
\[
\Gamma \vdash e : t
\]
means that in the context $\Gamma$, the type of $e$ is $t$.

\begin{frame} 
\begin{block}{Rule in the Type System}
\begin{center}
$
\inferrule*[]{
	\Gamma, x : t_1 \vdash e : t_2
 }{ 
 \Gamma \vdash \lambda x . e : t_1 \rightarrow t_2
}
$
\end{center} 
\end{block}

Then we would be able to go ``up" one step using the rule: \\

\begin{block}{Applied to Our Case}
\begin{center}
$
\inferrule*[]{
	\Gamma, x : \mathsf{int}\{v: v \geq 0\} \vdash x+1 : \mathsf{int}\{v: v \geq 0\}
 }{ 
 \Gamma \vdash \lambda x.\ x + 1 : \mathsf{int}\{v: v \geq 0\} \rightarrow \mathsf{int}\{v: v \geq 0\} 
}
$
\end{center} 
\end{block}
\end{frame}


\begin{frame} 
As we keep going up the tree, we will eventually get to a rule like: 
\begin{block}{}
\begin{center}
$
\inferrule*[]{
	\Gamma \vdash \forall x : b .\ \phi \Rightarrow \tau
 }{ 
 \Gamma; x: b \{ x : \phi \} \vdash \tau
}
$
\end{center} 
\end{block}

\textit{Under the context gamma: if for every $x$ in the base type $b$ for which the proposition $\phi$ holds, we can derive condition $\tau$, then in the context extended with $x$ being in the $\emph{refinement}$ type, we can derive $\tau$.}

Moving up along this rule lets us go from a refinement type, to a checkable \emph{implication} to pass to an SMT solver!
\end{frame} 






\begin{frame}{Tweaking the Rule} 
For refinement type systems, it is actually very important that we are allowed \emph{dependent} functions: 

\begin{block}{Then we would have a rule like:}
\begin{center}
$
\inferrule*[]{
	\Gamma, x : t_1 \vdash e : t_2
 }{ 
 \Gamma \vdash \lambda x .\ e : (x\!:\!t_1) \rightarrow t_2
}
$
\end{center} 
\end{block}

 That means that the type $t_2$ can depend on the value $x$.
\end{frame} 

\begin{frame}{Biderectional Typing} 
We cannot expect the programmer to write the exact types needed by the proof for every single sub-function. 

Therefore, the system differentiates types that can be \emph{checked} against a type that is given, vs types that can be \emph{synthesized} (or inferred). 

Synthesis and checking must maintain verification side-conditions $\tau$ to be passed up to the SMT solver.

Bidrectional type-checking allows the programmer to write type signatures for functions. Refinement checker can synthesize types of intermediate sub-expressions.
\end{frame} 


\begin{frame}{Refinement Inference}
In order to enable type polymorphism, and higher-order programming, we must go further. 

Type signatures are allowed contain ``holes" with unknown refinements 

Holes are replaced with \emph{Horn variables} 

Verification conditions now contain Horn variable applications as well as predicates. 

Rather than SMT solver, use a Horn Solver to perform \emph{fixpoint} computation to determine allowed refinements. 

Not merely \emph{validity} of a verification condition - instead, \emph{satisfying assignment}.

More complex: 

\end{frame} 


\begin{frame}{}
\begin{center}
$
\inferrule*[right=B-NonDet.1]{
\langle C_1 , s \rangle \Downarrow s'
 }{ 
\langle C_1 \oplus C_2, s \rangle \Downarrow s'
}
$
\qquad
$
\inferrule*[right=B-NonDet.2]{
\langle C_2, s \rangle \Downarrow s'
 }{ 
\langle C_1 \oplus C_2, s \rangle \Downarrow s'
}
$
\end{center} 
\end{frame}

In Python, this is only caught at run-time. In C or Rust this is caught at compile-time. The \textbf{Type System} saves us some headaches!

\begin{frame} 
We are interested in writing \emph{more correct} code. Thus, we would want to avoid the following kinds of \emph{common mistakes}: 

\begin{block}{}
\begin{itemize}
\item divide by zero
\item index an array outside its bounds (or try to use an element from an empty list/array)
\item run binary search on an unsorted list
\item use a data-structure before it is initialized
\item multiply matrices with incompatible dimensions
\item use a pointer after it is deallocated in memory
\item forget a base-case in a recursive function
\item general off-by one errors
\end{itemize}
\end{block}

\end{frame}


\section{Formal Verification Intro}
\begin{frame}{Formal Verification: Rapid Refresh}
\begin{block}{What is Formal Verification?}
\begin{itemize} 
	\item Program verification: Logically ``prove" correctness of a program
	\item labour-intensive process - Can involve manual encoding in e.g. Rocq, Agda, Lean, Idris
	\item Some tools for (partial) automation: Dafny, Viper, etc.
	\item Often rely on an SMT solver and/or Horn Clause solver
	\item ``very high level of reliability" BUT only as good as your mathematical model 
\end{itemize} 
\end{block}
\end{frame}

\section{Refinement Type Checking}
\begin{frame}{Refinement Types: Idea}
\begin{itemize}
\item
Type systems are useful for writing correct code, e.g. use \emph{int} for numbers, but for true/false use a \emph{bool} instead of 0 and 1.

\item
Can be more precise with our types: e.g. \emph{signed} and \emph{unsigned} ints. 

\item
But what if you need a \emph{non-zero} int? What about an int \emph{less than 5}? 

\item What about a type that depends on another? E.g. a index \emph{i smaller than the size n} of a list L? 

\item 
Can we extend the type system to cover the above cases? How complicated does the type system become? Can the compiler still manage it? 
\end{itemize}
\end{frame}




\begin{frame}{Intuitive Applications for Refinement Types}
Most useful when you can view the correct input to a function as a \emph{special case} of possible inputs:
\begin{block}{}
\begin{itemize}
\item division by zero: require \emph{non-zero} integers
\item index out-of-bounds error: list of given \emph{size}, index integer \emph{smaller than list size}
\item matrix multiplication issues: matrices of \emph{compatible dimensions}
\item uninitialized data-structure: mark data-structure as \emph{intialized} (e.g. require \emph{sorted} list for binary search)
\item general invariants can be encoded as \emph{maintaining type}
\end{itemize}
\end{block}
\end{frame}

\begin{itemize}

$\texttt{int} \{ v : v \not= 0\}$
\item
$\texttt{int} \{ v : v \geq 0\}$
\item 
$\texttt{int} \{ v : true \} $

$\texttt{bool} \{ v : v = (x+y = z) \}$ (variables $x,y,z$ in scope)

\section{Implementing Refinement Type Checking} 
\begin{frame}{Implementing Refinement Type Checking} 
Rules can be specified on a $\lambda$-calculus. 
E.g. start with simply-typed $\lambda$-calculus, can enrich it with e.g. arithmetic values and operations, branching, and recursion.

Programs represented as functions.

Good for representing functional languages (e.g. Haskell) but becomes trickier when dealing with imperative languages (e.g. Rust).
\end{frame} 

\begin{frame}{}
Our previous program can be represented by a $\lambda$-function: 
\begin{block}{Lambda representation}
$\texttt{abs} \equiv \lambda x. \texttt{ if } x < 0 \texttt{ then } -x \texttt{ else } x$
\end{block} 

Verifying the program then amounts to deriving that the above has the type: 
\begin{block}{}
\[
\texttt{abs} : \texttt{int} \rightarrow \texttt{int}\{v : 0 \leq v\}
\]
\end{block}
(Actually, that the function is a \emph{subtype} of the above type!)
\end{frame}

\begin{frame}{}
Typing arguments are represented through typing judgements: 
\begin{itemize} 
\item well-formedness
\item entailment
\item subtyping 
\item 
\end{itemize} 
\end{frame}

\begin{frame}{Implementing Refinement Type Checking} 
Rules can be specified on a lambda type calculus
\[
x : \texttt{int} ;
\texttt{one} : \texttt{int}\{v: v = 1\}
\vdash 
\texttt{add}\ x\ \texttt{one} 
\Leftarrow
\texttt{int} 
\{
v : x < v
\}
\]

\end{frame}

\section{Rust Intro}
\begin{frame}{Rust}
\begin{block}{What is Rust?}
\begin{itemize}
	\item Rust is a \textbf{systems} programming language
	\begin{itemize}
		\item low-level control
		\item fast / efficient
	\end{itemize}
	\item strongly-typed
	\item ``ownership" and ``borrowing"
\end{itemize}
\end{block}
\begin{block}{Special Sauce} 
Memory safety guarantees without garbage collection
\end{block}
\end{frame}



\begin{frame}[fragile]
\frametitle{Ownership and Borrow Examples}
\begin{lstlisting}[language=Rust]
foo(s); // foo takes ownership of s
bar(&t); // bar borrows t as read-only
baz(&mut u); // baz borrows u and can modify it
\end{lstlisting}
\end{frame}


\begin{frame}{Rust: Variable Scopes}
\begin{block}{} 
\begin{itemize}
\item Rust automatically calculates lifetimes
\item When an object goes out of scope, its resources are automatically freed
\item ``Resource Acquisition is Initialization" 
\end{itemize}
\end{block}
\begin{quote}
``resource is guaranteed to be held between when initialization finishes and finalization starts 
and to be held only when the object is alive"
\end{quote}
\end{frame}


\begin{frame}[fragile]
\frametitle{Drop example}

\begin{lstlisting}[language=Rust]
fn borrow_box(ibox: &Box<i32>)
\end{lstlisting}

\begin{block}{}
\begin{lstlisting}[language=Rust]
fn create_box() {
    let my_box = Box::new(1i32);
    borrow_box(&my_box);

    // my_box memory freed here
}
\end{lstlisting}

\end{block}

\end{frame}


\begin{frame}{Borrowing}
\begin{block}{Rust Ownership and Borrowing}
\begin{itemize} 
	\item One owner
	\item One read/write borrow
	\item Multiple read-only borrows
	\item When lifetime ends, item is returned
\end{itemize} 
\end{block}
\end{frame}

\begin{frame}[fragile]
\frametitle{Multiple Borrows Example}
\begin{lstlisting}[language=Rust]
fn calculate_length(s : &String) -> usize
\end{lstlisting}

\begin{block}{}
\begin{lstlisting}[language=Rust]
    let mut s = String::from("hello");
    
    let t1: &mut String = &mut s;
    // <@\textcolor{blue}{t1 never used again, gets dropped}@>
    let t2: &mut String = &mut s;

    let len = calculate_length(t2);
 \end{lstlisting}
\end{block}

\end{frame}


\begin{frame}[fragile]
\frametitle{Not Fine}
\begin{lstlisting}[language=Rust]
fn calculate_length(s : &String) -> usize
\end{lstlisting}

\begin{block}{}
\begin{lstlisting}[language=Rust]
    let mut s = String::from("hello");
    
    let t1: &mut String = &mut s;
    // <@\textcolor{red}{t1 used again later, still active}@>
    let t2: &mut String = &mut s;

    let len = calculate_length(<@\textcolor{red}{t1}@>); // fails
 \end{lstlisting}
\end{block}

\end{frame}




\begin{frame}{Unsafe Rust}
\begin{block}{Unsafe Rust}
\begin{itemize} 
	\item sections of code can be tagged `unsafe' - indicates borrow checker does not apply
	\item necessary part of Rust - e.g. de/allocation optimizations, cyclic references, call external code
	\item unsafe code should be wrapped in a safe API
	\item lots of the Rust standard library uses `unsafe'
	\item you can usually find a standard safely wrapped version of whatever unsafe thing you want to do
	\item provides a challenge for formal verification
\end{itemize} 
\end{block}
\end{frame}

\begin{frame}[fragile]{Aliasing Problem}
\begin{block}{C program}
\begin{lstlisting}[language=C]
void increment_both(int *x, int *y)
{
    *x = *x + 1; 
    *y = *y + 1;   
}
 \end{lstlisting}
\end{block}

\begin{block}{Calling ``increment both" with the same variable twice}
\begin{lstlisting}[language=C]
int a = 0;
increment_both(&a, &a); 
\end{lstlisting}
\end{block}
\end{frame}

\begin{frame}{Proof Difficulty}
\begin{itemize}
\item
Aliasing could happen anywhere in the program
\item
Correct usage of increment\_both relies on \emph{non-local} information!
\item
Strategies exist, involving e.g. separation logic
\item But in Safe Rust, mutable references can \emph{never alias}
\item Rust also strongly typed, and borrows must be marked read / write
\end{itemize} 
\end{frame}

\begin{frame}{Unsafe Rust and Verification} 
\begin{itemize}
\item 
Unsafe Rust is essential for functioning of Rust 
\item 
It is more difficult to verify since we do not have the safety guarantees \emph{inside} unsafe blocks
\item 
But we can still isolate (un)safety, make assumptions, prove separately
\item 
Some tools for unsafe Rust exist
\end{itemize} 
\end{frame} 


\begin{frame}{Flux} 
\begin{itemize}
\item Refinement Type Checking (liquid types) - statements to be proven are encoded as types
\item Runs as a Rust compiler plugin 
\item Less powerful than Prusti but much faster and with fewer annotations
\item Concept of "strong mutability / structural mutability" - e.g. whether a vector's length can change or just the values of its elements
\item No quantified statements - cannot verify e.g. sortedness of list
\end{itemize}
\end{frame}
